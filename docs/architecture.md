# Kvarm architecture

This document describes Kvarm as it is built: one Cloudflare Worker that serves git smart-HTTP, a versioned REST API, an MCP server and server-rendered repository pages on top of Cloudflare Artifacts. The [README](../README.md) covers deployment, the CLI, the API reference and measured limits; this document explains how the parts fit together and which rules they follow.

**Citations.** Source comments cite this document by section number, for example "architecture §11.4" or "§0.1/§0.3". "Invariant N" means §2.N. A few comments say "STEER v2 §0.x"; that is an older name for the §0 decisions and points at the same sections. `node scripts/check-architecture-refs.mjs` checks that every numbered citation in the repository resolves to a heading here (or in the document the citation names), and the test suite runs it.

**Budgets, the registry of record and the risk rules.** Tests and scripts cite "budget rows": the per-endpoint work budgets. §10 describes the budget model, `scripts/lib/cost-catalog.mjs` holds every budgeted row as a machine-checked spec, and [`docs/benchmarks/README.md`](benchmarks/README.md) lists the measured counters per endpoint next to their budgets. The operation registry of record is `packages/ops/src/index.js` (every operation with its REST route, MCP tool and CLI command; `kvarm help <group> <verb>` prints one entry), and the risk rules are the code and tests of `packages/review`. `scripts/cost-sweep.mjs` reads the budget rows from a markdown budget table given as `--cost-md`; `scripts/mcp-agent.mjs` and `scripts/dependencies-e2e.mjs` compare the registry against a markdown registry table only when `--api-doc` names one.

## 0. Design decisions

These decisions shape the whole codebase. Later sections refer back to them.

### 0.1 One owner per concern

- **Overlap and conflict prediction** belongs to the Nexus forecast service, `services/intents/forecast.ts`. Nothing else computes overlap. The candidates service ranks and diffs candidates and reads overlap from the Nexus index (§4, §11.2).
- **One operation registry.** `packages/ops` defines every operation once. Each entry is a REST endpoint, an MCP tool and a `kvarm` CLI command, so the three surfaces cannot drift (§4, §11.6).
- **Fencing** belongs to the merge queue. Publication leases (`do/mergeLock.ts`) and the generation/owner-fenced claims of CI jobs and agent tasks (`services/fencing.ts`) share one model: every claim has a generation, and a late report or release from an earlier holder is rejected (§11.4).
- **Arenas are candidate sets.** An arena is an explicit set of 2–8 candidate workspaces inside the candidates service, not a separate subsystem (§11.7).

### 0.2 Out of scope for this version

The following are designed but not built; the README lists them under "Deferred roadmap": audit export (`get_audit`), contract capsules, semantic packets, hotspot suggestions, priority credits, resource lifecycle, advisory low-signal test flags and the collaborative UI pass. Code paths that would serve them either do not exist or are documented as inert.

### 0.3 The checks gate

Merge, queue and composition code never talks to a concrete check producer. It asks one interface, `requiredChecksFor(repo, treeSha, configId)` in `services/checksGate.ts`, which returns the required check set for an exact tree and its state. Producers register with the gate: `kvarm/guard` (`services/checks.ts`) and user-owned CI (`services/ci.ts`). With no producers the required set is empty and its state is `success`, so a merge is gated by mergeability alone.

This inversion is why the merge engine and the integration train do not depend on CI: adding or removing a producer changes no merge, queue or composition code. A change with merge policy `auto` merges when every required check of its exact tree passes (§2.5).

**What a passing `kvarm/guard` proves.** The guard reads the change's own edits (merge-base tree to head tree) under fixed budgets: the first 100 changed files it reads, each side up to 64 KiB (`GUARD_BUDGETS`), added lines up to 4,096 characters (`GUARD_LIMITS.maxLineChars`), over the compare body's file list (which can itself be truncated). It covers changed text files only: removed files (beyond the deleted-test rule), lockfiles, submodule entries and binary content (a NUL byte in the first 8,000 bytes of the new side; text replacing a binary file is scanned in full as added) are outside its rules by design and do not make a scan incomplete. Its conclusion is `success` (every rule ran over everything it covers and found nothing), `failure` (a secret or CI-gaming finding) or `neutral`. Neutral covers two different things: advisory findings such as `dependency/typosquat` and `dependency/non-registry` on a fully read change, and an incomplete scan (files past the file budget, past the per-file prefix or the per-line limit, unreadable blobs, or a truncated file list). Both map to run status `success`, so on its own a passing guard only proves that the content it read was clean. The summary (version `guard/v2`, where a cut long line became incomplete) says which: `complete` is false for an incomplete scan, `uninspected` lists the paths with a reason (`over-file-budget`, `prefix-only`, `line-prefix`, `unavailable`; at most 50 named, all counted) and whether the list was truncated, and `title` starts with `incomplete:`. The commit status lists such checks in `incomplete`, and the gate's `kvarm/guard` entry carries `incomplete: true` with the uninspected count. Raising the budgets is not the answer to an incomplete scan; a branch rule decides what it means for a ref.

**Guard completeness per branch rule.** Each branch rule (§11.1) has `guardCompleteness`: `advisory` (the default, and every rule created before migration `0023`) reports an incomplete guard but lets it pass; `required` makes publication into a matching ref refuse it like a failure, with `409 GUARD_INCOMPLETE` from an explicit or auto merge and a queue ejection with reason `GUARD_INCOMPLETE` (judged when the train prepares the candidate and again right before it sends the pack, against the rules current then; like `CHECKS_FAILED`, the ejection breaks pins held on that head). Across several matching rules `required` wins. Advisory-only neutral findings never count as incomplete. The refusal is terminal for that head: the same head is judged the same way again, so the change has to be split or reshaped so the guard can read all of it.

### 0.4 Review, composition and decisions

- **Agent review.** Agent principals may review. A per-repository policy requires N approving reviews from principals other than the author; each agent principal records a nullable `modelFamily`, and reviewer assignment prefers a family different from the author's. Reviewer disagreement, a request for changes, a touched protected path or branch rule, and a final arena selection each open an escalation that only a human can resolve. Protected targets still need human approvals. Approvals bind to the exact head and are revalidated immediately before publication (`services/reviews.ts`, `services/reviewGate.ts`, §9).
- **Composition.** `POST candidates/compose` folds compatible pieces (paths) from several candidate attempts onto the base head with gitops `merge3`, creating a composed workspace ref and change. The composed tree runs the same exact-tree required checks as the train. A clean merge whose required check fails is a **semantic conflict**, reported separately from textual conflicts (`services/compositions.ts`, §11.4).
- **Decisions and context.** Besides attribution notes, agents record decisions `{task?, paths[], chosen, rejected[], reason, actor, at}` in D1, indexed by task and by path. The MCP tool `get_context(task|path)` returns earlier decisions and rejection reasons, bounded, paginated and checked by the shared authority (`services/decisions.ts`, `services/attribution.ts`).

### 0.5 Execution posture

Kvarm does not call a hosted model. Agents can run where their users run them (Claude Code, Devin, a laptop, an on-premises runner) and coordinate through git workspace refs, MCP tools, declared intents, the merge queue and task dispatch. The opt-in fleet additionally provides Cloudflare-hosted Linux build environments and resumable agent sandboxes (§0.6). CI remains user-owned: `kvarm runner` claims jobs on the user's machine. A claim carries the job's provenance (its change, head ref, whether the commit is the change head or a platform-prepared merge commit, whether a human or an agent opened the change, and whether any agent token grant matches the head ref). The runner's execution-trust policy uses it to run the job on the host, run it in a docker or podman container, or refuse it and report a failure, before any of the job's code reaches the machine; by default only heads of human changes on refs no agent credential may write run on the host. The pusher of a head is not recorded, so the policy reasons about who could have pushed it.

Cloudflare Containers (public beta) host an opt-in hosted-CI runner lane and Linux-only fleet workloads (§0.6). The Container CI runner (`containers/ciRunnerSandbox.ts`) is one Durable Object per repository; it is the hosted lane for repositories whose admins enable it (`POST …/ci/hosted/enable`). Every path that queues CI jobs kicks the object's alarm, and the alarm drains the queue in one container session through the native `ctx.container` API — the same claim → snapshot checkout or warm sync → run → report loop as `kvarm runner`, with a small number of concurrent workers. The first session installs the runner and toolchain and saves a container snapshot at the first prepared workspace; a later session starts from that snapshot and resumes without setup or checkout. Kicks that arrive mid-drain coalesce, and the alarm makes an interrupted session self-healing. The object also serves the single-run admin showcase (`POST …/ci/container-runs`). The hosted lane runs under a dedicated non-admin service identity with an explicit write grant on each opted-in repository; each drain mints a short-lived repository-scoped PAT (2 h expiry, revoked at the end of the drain, swept on the next mint), passed only through the runner exec environment and never written to the filesystem or a snapshot. Every hosted CI job runs in the throwaway container (`trust: 'all'`), including agent-authored work a user's host runner would refuse; the container is the isolation boundary (SECURITY.md). The user-owned `kvarm runner` keeps racing on the same fenced queue, so neither lane is a single point of failure. `EnvironmentBuilder` and `AgentSandbox` provide the fleet's reusable Linux build environments and resumable sandboxes; runtime credentials stay in their owning Durable Object and never enter build snapshots or container filesystems.

### 0.6 Agent fleet

The opt-in fleet provides reusable Linux build environments and resumable agent sandboxes on Cloudflare Containers. Environment builds run from immutable repository snapshots with internet disabled except for explicitly allowed package hosts; successful builds become reusable container snapshots. A sandbox restores that build once, persists workspace state across sleep/wake snapshots, and keeps its agent token only in the owning Durable Object. Each start or wake receives a fresh, workspace-ref-scoped token; sleep revokes it. Wake fetches the workspace and base refs and fast-forwards only a clean local ancestor, never resetting agent work. Allowed-host changes take effect on the next start or wake. Idle and run-window expiry sleep a sandbox; explicit discard deletes its snapshot state, while sleeping sandboxes are retained for up to 25 days. Commands follow environment deny/approval policy and are audited; files remain confined to `/workspace`. Non-Linux environments are rejected until another `SandboxProvider` implementation exists. The Environments and Fleet pages follow the session rules of §11.1: every form post from a signed-in browser (environment create, edit, rebuild and archive, sandbox sleep and discard, and an approval decision) carries the session's CSRF token, and one without it is refused with `403` before anything is written.

Agent-facing capabilities follow one test: they change a surface every user already touches (merge, review, queue, forecast, CI, status), work through the existing identity, gate and cost machinery, and help a user who never thinks about agents.

## 1. System shape

```
git client  --smart-HTTP-->  git gate (routes/git.ts) ------------------------> Artifacts (git storage)
REST client --/api/v1/*-->   Hono routers (thin) --> services/* (all logic) --> Artifacts reads (binding)
MCP client  --/mcp------->   MCP tools (thin) ----/                         \-> Artifacts writes (receive-pack client)
                                  D1 (registry and state)   Cache API (content-addressed)   R2 (snapshots)
Artifacts push event --> queue kvarm-events --> queue() consumer --> cache purge, snapshot build, kvarm/guard,
                                                                    CI dispatch, environment builds, change head refresh, train kicks
CI pipeline workflow --> ci_jobs (D1) <-- claim/report -- `kvarm runner` on the user's machine
                                            <-- drain ---- CiRunnerSandbox Durable Object (opt-in hosted container lane)
merge queue --> parallel preparation and checks --> short MergeLock publication lease --> receive-pack with expected old value
workspace intents and pushes --> Nexus path index --> advisory forecast --> opt-in pinned dependencies
```

**Layering.** Routers (`routes/**`) and MCP tools (`mcp/server.ts`) are thin adapters. All behavior lives in `apps/platform/src/services/*.ts`; service functions return `ServiceResult<T>` (`{ok: true, value}` or `{ok: false, status, error}`). Pure algorithms live in `packages/*` and are tested in Node.

**Bindings.** D1 `DB` (registry and state), Artifacts `ARTIFACTS` (git storage, namespace `default`), R2 `SNAPSHOTS`, the `EVENTS` queue (`kvarm-events`, with `kvarm-events-dlq`), the Workers Rate Limiting bindings `READ_LIMITER` and `WRITE_LIMITER`, the Durable Objects `MergeLock`, `CiRunnerSandbox`, `EnvironmentBuilder` and `AgentSandbox` (plus `TokenCache` and `RateLimiter`, which stay exported to keep the Durable Object migration history intact but are no longer used), and the Workflows `snapshot-builder`, `ci-pipeline`, `merge`, `repo-import` and `environment-build`.

### 1.1 Git gate

`routes/git.ts` serves `https://<host>/<owner>/<repo>.git/*`: `info/refs`, `git-upload-pack` and `git-receive-pack` (smart HTTP v0 and v2). Web paths are the same without `.git`.

- **Authorization first.** Personal access tokens and agent tokens arrive as the basic-auth password; anonymous reads are allowed for public repositories. Every request goes through the shared authority (`resolveRepoAccess`, §11.1) before any cached body, token mint or upstream fetch.
- **Streaming.** The proxy streams both directions and buffers nothing; pack generation stays inside Artifacts. Memory and CPU stay flat regardless of repository size.
- **Upstream tokens.** Artifacts git tokens are cached per repository and scope in the Cache API (`artifacts/tokens.ts`); a miss mints through the Artifacts binding directly, once per colo per refresh window. Anonymous and authenticated reads share the read-only token, because platform authorization has already happened by then.
- **Edge-cached advertisements.** `info/refs` for public repositories is cached briefly, keyed by the repository view generation that a confirmed push advances before its reply ends (§9 push freshness).
- **Receive-pack gate.** Before object data streams, `services/receivePackGate.ts` parses the bounded command header and enforces repository access, agent workspace ownership, branch rules, platform-reserved namespaces (`refs/heads/agents/**`, `refs/heads/kvarm-ci/**`, `refs/heads/kvarm-revert/**`) and non-fast-forward rules (§11.1).
- **No Durable Object on the hot path.** Rate limits use the Workers Rate Limiting bindings; tokens come from the Cache API.

## 2. Invariants

### 2.1 Artifacts is the only git store

Reads go through the binding (`readTree`, `readBlob`, `readCommit`, `readFile`, `log`). Every server-side write (merge commits, notes, ref moves, workspace refs) goes through the smart-HTTP `git-receive-pack` client in `packages/gitops` (`services/gitwrite.ts`, the `GitPusher`), with the ref's expected old value. Kvarm never reimplements git storage.

### 2.2 D1 holds registry and state, never file content

Schema changes are new numbered migrations in `apps/platform/migrations/` (§6). Migrations are additive; existing data is not dropped or altered.

### 2.3 Content-addressed caching

Anything derived from immutable SHAs is cached in `caches.default` under synthetic keys `https://kvarm.internal/<kind>/...`, for example `treediff/<baseTree>/<headTree>`, `filediff/<oldBlob>/<newBlob>` and `risk/<baseTree>/<headTree>` (`cache/compare.ts`). These entries never need invalidation. Responses for moving refs get short TTLs and are invalidated by pushes. A cached body is served only **after** the per-request authority lookup (§10, §11.1); a cache hit never substitutes for authorization, and repository metadata is not exempt. When derived output changes shape, the cache key version advances so old entries are never adopted.

### 2.4 Budgets everywhere

Every walk (tree diff, merge-base search, snapshot build, guard scan) has explicit read, size and time budgets and returns `truncated: true` with a reason instead of failing or hanging. Per-request binding calls stay below the Workers subrequest limit.

### 2.5 Merge policy belongs to the contributor

`change_sets.merge_policy` is `auto`, `draft` or `review` (default `review`). `auto` merges through the queue when every required check passes; `draft` never merges, even after conflict resolution; `review` stays open until an explicit `POST …/merge`. Changes that Kvarm generates (conflict resolutions, compositions, reverts) declare their policy explicitly, and Kvarm never overrides a contributor's policy. A revert change set (kind `revert`, §11.9) is `draft` unless its requester asks for `review` or `auto`. The required check set comes from the checks gate (§0.3).

### 2.6 Stable versioned JSON and shared authorization

Endpoints live under `/api/v1`, use camelCase JSON with ISO 8601 UTC timestamps, and fail with `{error, code?}`. Every surface uses one repository authorization service (§11.1). Public reads stay possible; unauthorized access to a private repository is concealed (it answers exactly like a missing one).

### 2.7 No secrets in code or logs

Tokens are stored as SHA-256 hashes and shown once at creation. Webhook signing secrets are also shown once, but the platform must sign with them, so they are stored AES-GCM encrypted under a key derived from the `WEBHOOK_SECRET_KEY` Worker secret (§11.5). Worker secrets stay in the secret store. Cost headers and logs carry counts, never identifiers or secrets. `kvarm/guard` findings never include the secret value.

### 2.8 Cost-efficient by construction

Requests record work counters and stay within documented budgets (§10). Cached content is preferred over D1, Artifacts and Durable Objects; statements and messages are batched; N+1 queries are avoided; background work is bounded. Access revocation and tenant isolation take precedence over warm-cache shortcuts.

### 2.9 One owner per concern

Overlap signal, the operation registry and fencing each have exactly one owner (§0.1). Merge, queue and composition depend only on the checks gate (§0.3).

### 2.10 Check evidence identity and reserved namespaces

- The gate answers `kvarm/guard` only from the publishing change's own recorded run. A run judged against a different merge base than the publication's plan answers pending, never success, and a newer clean run from another change at the same head never masks an earlier failure.
- A bounded gate window that may have truncated reports pending; bounded reads never prove completeness by omission.
- Repository CI commands run in a minimal child environment without credential variables. Runner report summaries are bounded by the UTF-8 size of the complete serialized JSON and keep the job conclusion.
- `refs/heads/kvarm-ci/**` (CI staging), `refs/heads/agents/**` (agent workspaces) and `refs/heads/kvarm-revert/**` (revert change set heads, §11.9) are platform-reserved. Receive-pack rejects human pushes to them in every repository, and agent pushes to `kvarm-revert/**` whatever the token's grant; platform writes use the direct writer.

### 2.11 Fast dev loop

The platform adds no avoidable wall-clock latency to merge, validation or CI paths. Answers are synchronous (an explicit merge publishes inside the request) or recorded (`kvarm/guard` and CI dispatch are written by the push-event consumer), and the gate answers pending until a verdict is recorded, never a stale one. Mergeability is probed once per (target, head) and then served from the content-addressed cache; checks-gate questions in one request share one bounded D1 batch. CI is fast by construction: snapshot checkout instead of clone, warm working directories reused across runner jobs, and container snapshot reuse. Turnaround is measured in [`docs/benchmarks/README.md`](benchmarks/README.md), not asserted.

## 3. Packages (pure, Node-tested)

- **`packages/gitops`**
  - `pack.ts`: packfile v2 writer, including the empty pack for pure ref moves.
  - `receivePack.ts`, `reportStatus.ts`, `refUpdates.ts`, `lsRefs.ts`: the smart-HTTP receive-pack client. It reads the advertisement, sends `<old> <new> <ref>` commands with `report-status`, and parses `unpack ok` / `ok <ref>` / `ng <ref> <reason>`. HTTP 200 alone is never success.
  - `mergebase.ts`: budgeted merge-base search over a commit reader (`git merge-base --all`).
  - `virtualBase.ts`: the virtual merge base of a criss-cross history (§3.1).
  - `merge3.ts`, `mergeText.ts`: tree-level three-way merge plus line-level diff3 of blobs, returning merged entries and `conflicts[]` by kind (content, add-add, modify-delete, rename, type change, binary). It is also the engine of composition (§0.4) via `compose.ts`.
  - `resolve.ts`: deterministic conflict resolution, the stage between git's merge and a human or agent. Rules: non-overlapping hunks (already merged by diff3), the identical change on both sides, identical add-add, and whitespace-only conflicts (the target's variant wins). Lockfile conflicts are never resolved here; they are marked `needsRegeneration` and dispatched as a task (`services/conflicts.ts`, `services/tasks.ts`).
  - `tar.ts`: streaming ustar/pax writer for snapshots.
  - `notes.ts`: git-notes commits on `refs/notes/kvarm-attribution` (path = commit SHA).
  - `treediff.ts`: pruned tree diff with one global read limit.
  - `revert.ts`: the tree `git revert` commits, as the inverse three-way merge (base = the reverted commit, ours = the target, theirs = its first parent or an explicit commit), with no resolver (§11.9).
- **`packages/diffcore`**: line diffs and hunks with work budgets.
- **`packages/review`**: `classifyFile` and `rateChange` (risk score, level and tags such as `ci-config`, `test-deletion`, `lockfile`, `new-dependency`, `generated`, `mechanical`, `security-sensitive`, `large`), and `guard`, the `kvarm/guard` rules: secrets (known token formats including `kvarm_pat_`/`kvarm_agt_`, private keys, high-entropy assignments), CI gaming (`|| true`, `continue-on-error: true`, deleted or skipped tests) and suspicious new dependencies. Its result reports `complete` and the paths it did not fully inspect (§0.3). `semantic.ts` is the bounded import/export/contract-file reader behind the Nexus semantic signal (§11.2).
- **`packages/issues`**: issue references in change text (closing keywords, lists, trailers, `owner/repo#N`; negated fixes and code are mentions only), the issue number a branch name carries, and issue fingerprints, including `checkFingerprint(name)` and `guardFingerprint(rule, path)`, the one fingerprint of a check and of a guard finding.
- **`packages/ops`**: the shared operation registry (§0.1): every operation's REST route, MCP tool name, CLI command and JSON schema.
- **`packages/ui`**: server-rendering helpers for the existing pages.

### 3.1 Criss-cross merges

When two tips have several best common ancestors (agents merging from each other, or from pinned workspaces, produce these), Kvarm merges the way `git merge` does with its default strategy (ort, which `-s recursive` also means since git 2.34): the merge bases are merged pairwise into a virtual commit, recursively when a pair has several bases of its own, and the tip merge runs against the virtual commit's tree (`virtualBase.ts`). Mergeability and the merge endpoint report every base in `mergeBases`; `mergeBase` stays the first of them (bases are sorted by object id), and that real commit is the `kvarm/guard` base. The virtual tree cannot be the guard base because its objects are never stored; diffing from one real base over-reports (it also shows what arrived through the other bases, which the target already has) but never hides an edit of the change's own, while diffing from the target tip would show the target's later work as reverted.

- **Conflicts inside the virtual ancestor follow git.** A text conflict between two bases is written into the virtual tree with its markers (`Temporary merge branch 1/2`, 7 + 2 × depth wide), so when both tips settled it the same way the markers cancel and the outer merge is clean, and when they settled it differently the outer merge conflicts on that path instead of silently taking one base's side. A modify/delete keeps the original file; binary, symlink and submodule conflicts keep the base version; two different added files are content-merged against an empty base; bases without a common ancestor merge against the empty tree. Refusing every inner conflict was the alternative and was rejected: it would refuse exactly the histories where a virtual ancestor matters. Inner merges never apply the deterministic resolution rules of `resolve.ts`; only the outer merge does.
- **What is refused.** An inner conflict that git settles with rules `merge3` does not model at depth (rename/rename, rename/delete, rename/add, directory-rename splits, file/directory and type changes) stops with `virtualConflict` instead of producing a tree that could differ from git's. Bases are merged in object-id order because commit readers carry no dates; git merges oldest first. The order only changes the labels and nesting of markers inside the virtual tree; the corpus shows no outcome difference.
- **Budgets.** `MERGE_BUDGETS.maxMergeBases` (8 per pair, the outer pair included) and `maxVirtualDepth` (3; the outer bases merge at depth 1) bound the shape; every inner merge-base walk and merge spends the same commit, tree, blob and created-bytes budgets as the outer merge, so the request-path total is unchanged (inner walks are charged only for commits the outer walk has not read, and the outer merge reuses the trees the inner merges fetched). Exceeding `maxMergeBases` or `maxVirtualDepth`, or a `virtualConflict`, is `422 MULTIPLE_MERGE_BASES` with `reason` set to that name; exhausting a shared read or byte budget is `MERGE_TOO_LARGE` as for any merge. Virtual-base objects are merge inputs only and are never published: a clean merge's tree is closed over objects the outer merge created plus objects already in the repository. Composition (§0.4) diffs a criss-cross piece against its virtual base and records every base in the piece's `mergeBases`; the virtual merges spend the composition's own tree, blob and byte budgets before the pieces are folded.
- **Parity evidence.** `scripts/conflict-corpus/crisscross.mjs` builds criss-cross commit graphs (clean, cancelling, real conflicts, modify/delete, add/add, binary, three bases, nested depth 2, unrelated bases, and seeded random cases); `packages/gitops/test/crisscross.corpus.test.ts` requires the identical tree, or the identical conflict set, to `git merge-tree --write-tree` of the two tips, which runs the same ort machinery as `git merge`.

## 4. Platform modules (`apps/platform/src`)

- **Access:** `services/access.ts` (credential and repository resolution, `resolveRepoAccess`, `authorizeRoute`), `services/authz.ts` (the shared policy), `services/orgs.ts`, `services/orgRepos.ts`, `services/grants.ts`, `services/agents.ts`, `services/branchRules.ts` (§11.1); human sign-in in `auth/workos.ts` (WorkOS AuthKit, sealed sessions, cross-origin and CSRF defenses), `auth/sealed.ts` and `services/identity.ts` (provisioning and explicit linking, §11.1).
- **Reading code:** `services/compare.ts` resolves refs to commits and trees, diffs trees over the Artifacts binding, adds per-file stats, per-file diffs and risk from `packages/review`, and caches by content (§2.3, §9). `services/contents.ts` serves trees and files; `services/snapshots.ts` and `workflows/snapshotBuilder.ts` build and serve snapshot tarballs (§11.5).
- **Changes:** `services/changes.ts` implements change requests over `change_sets`: create, list, get, update, close, head refresh on push, risk rating, mergeability and the merge endpoint that honors the merge policy (§2.5, §5). `services/reverts.ts` builds revert change sets and `services/incidents.ts` receives signed incident webhooks that open them (§11.9).
- **Checks and CI:** `services/checks.ts` (check runs with tree identity, the `kvarm/guard` evaluation and the commit status rollup) and `services/ci.ts` with `workflows/ciPipeline.ts` (`.kvarm/ci.json` at the immutable head becomes queued check runs and fenced runner jobs; a required first-attempt failure requeues one retry of the same head and tree). Both register as checks-gate producers (§0.3). `services/flakes.ts` records the flakes whose retry passed and holds the per-name quarantine state; `services/hostedCi.ts` is the opt-in hosted lane's settings, service identity and ephemeral runner credentials, and kicks the container drain.
- **Merging:** `services/merge.ts` plans a fast-forward or a two-parent merge commit over `merge3` outside any lease, asks the checks gate about the exact tree, and publishes the one target ref through the `GitPusher` with the target as expected old value; a moved target is `STALE_TARGET` and is re-planned. `services/conflicts.ts` records conflict state and dispatches `resolve-conflict` tasks.
- **Merge queue:** `services/queue.ts` with `do/mergeLock.ts` and `services/trainKick.ts` runs the bounded integration train (§11.4). It never holds a publication lease while checks run.
- **Events:** `services/events.ts` and the Worker's `queue()` handler process push events with independently replayable effects (§11.5); `services/pushFreshness.ts` makes a confirmed push visible before its reply ends (§9). `services/webhooks.ts` and `services/webhookSafety.ts` deliver platform events to outbound webhooks through the same queue and the Worker's `scheduled()` handler (§11.5).
- **Agents and coordination:** `services/workspaces.ts` (workspace lifecycle on `refs/heads/agents/<workspaceId>/<slug>`, §9), `services/intents/*` (the Nexus index and forecast, §11.2), `services/candidates.ts` and `services/compositions.ts` (candidate diffs, ranking, arenas and composition, §0.4, §11.7), `services/dependencies.ts` and `services/dependencyGate.ts` (pinned dependencies, §11.3), `services/tasks.ts` (agent tasks claimed under fenced leases), `services/reviews.ts` and `services/reviewGate.ts` (§0.4), `services/attribution.ts` and `services/decisions.ts`.
- **Issues:** `services/issues.ts` files issues (fingerprinted reports count occurrences on the open issue), links them to changes from the change's title, body and head branch and to workspaces created for them, and closes confirmed `closes` links inside the merge record (`mergedRecordStatements`) only for merges into the default branch. Signal owners (flakes, quarantine, guard) file and verify-close issues with `issueSignalStatements` and `resolveSignalStatements` inside their own batches. The flake registry was the first: `reportJob` files or counts a registered flake on the check's issue in its report batch (`flakeIssueStatement`, keyed by the flake row that batch inserted), `quarantineCheck` keeps an issue open for a quarantined check and `restoreCheck` closes it as `restored`. The guard is the second: the `issue-guard` push effect (`guardScanStatements`) scans a default-branch push that did not come from the publication path (a merge the platform published is recognized by its recorded merge commit) with the same `kvarm/guard` evaluation a change gets, files or counts one fingerprinted issue per failing finding (`guardFingerprint`), and closes one as `verified`, from a complete scan only, when a later push changes the path without triggering the rule again. `createComment` stores plain discussion, agent-attributed, with the newest 50 on the issue detail. `dispatchIssue` creates a `fix-issue` agent task (one live task per open issue, with its `kvarm.task.created` event); `services/tasks.ts` claims it into a workspace at the default branch linked to the issue and declaring its paths, and completes it once that workspace has opened a change. Every batch that closes issues also retires their live tasks: `completed` when the claimant's workspace merged, `obsolete` otherwise.
- **MCP:** `mcp/server.ts` builds an `McpServer` with the stateless `WebStandardStreamableHTTPServerTransport`, one server and transport per request, authenticated by Bearer token. Every tool comes from the operation registry and calls the same services as REST.
- **Cost:** `cost/meter.ts` (§10).
- **CLI (`apps/cli`):** snapshot checkout with git clone fallback, the user-owned CI runner with warm working directories, `kvarm status`, and every registry operation as `kvarm <group> <verb>`.

## 9. Pinned behaviors

- **Compare.** Paginated responses carry `nextCursor`, and `totals` describe the whole reported comparison, never one page. A compare within its read budget reports `totalsComplete: true` with exact totals; a compare truncated by its budget reports `totalsComplete: false`, and its `totals` are a labeled lower bound over the discovered subset. Responses carry `x-kvarm-cache: hit|miss|bypass`; `?nocache=1` is honored for instance admins only, skips cache reads and writes, and is the method for cold timings. Per-file line stats appear for up to 300 changed files (above that, `statsOmitted: true`). Files over 4 MiB are `tooLarge`. Budgets: 2,000 tree reads and 20,000 changed files, then `truncated: true`.
- **Compare performance gate.** On the 1M-changed-line fixture, the cold compare file list must answer with p50 under 500 ms over 10 runs, and no request may exceed 30 s. If the gate failed twice, the planned fallback was per-commit path-to-hash manifests built on push. The gate is met without the fallback; see [`docs/benchmarks/compare.md`](benchmarks/compare.md).
- **Push freshness.** After a protocol-confirmed receive-pack (complete report, `unpack ok`, at least one `ok <ref>`), the gate advances the repository's view generation and `pushed_at` and awaits both (bounded) before the client sees the end of the reply. HTTP 200 alone, `ng`, fatal and truncated reports change nothing. The push-event dispatcher repeats invalidation and records effect completion.
- **Snapshots.** Default-branch pushes build eagerly; other refs build on explicit demand. `kvarm checkout` prints `source: snapshot` or `source: clone`.
- **CI.** Runner job leases last 120 s by default, renewed by heartbeat. A `.kvarm/ci.json` has at most 16 jobs; job names may not start with `kvarm/`. A failed required, non-quarantined runner check gets exactly one automatic retry of the same head and tree; a pass on attempt 2 records a flake entry, a second failure blocks as before, and a quarantined check still runs but its runs never satisfy or block a required-checks gate. The hosted container drain runs two workers per repository.
- **Merge policy and the queue.** Enqueueing a `review` change approves its current head only; configured separate-review requirements remain additional gates. A draft cannot be enqueued (`409`). A head change stales approvals. A fast-forward merge reports `mergeCommit` equal to the head.
- **Workspaces.** The workspace ref is created server-side at the base head when the workspace is created. Abandoning a workspace deletes its ref and sets its status to `abandoned`; nothing is deleted automatically. Tasks are repository-scoped.
- **Attribution and decisions.** An attribution note is `{agent, session, promptHash, model?, actor, at}` on `refs/notes/kvarm-attribution`. Decision records and `get_context` are described in §0.4.
- **Provenance evidence levels.** The note records what a caller asserted. Kvarm cannot observe which model produced a commit, so every attribution reply (`GET`/`POST commits/:sha/attribution`, the audit export) carries `evidence {level, reasons, principal, tokenKind, tokenPrefix, runId, keyId}`, computed server-side at write time (`services/provenance.ts`) and stored in D1, never taken from the request:

  | level | what it proves |
  | --- | --- |
  | `declared` | The agent or caller asserts a model and session. Nothing binds the record to the submitter: a human credential writing agent metadata, agent A naming agent B, or a note on the ref that Kvarm did not write. |
  | `authenticated` | The credential proves which Kvarm principal submitted the record: an agent token of the agent it names, or a human naming themself. It proves who submitted it, not which model ran or what the prompt was. |
  | `verified` | A trusted execution service signed evidence linking the repository, the submitting principal, run, model, input identity (the prompt hash) and the produced commit, and the record is also authenticated. |

  The levels are a ladder: evidence that fails verification (unknown or revoked key, bad signature, a field that differs from the signed one) leaves the record `authenticated` or `declared`, and `reasons` says why (`no-signed-evidence`, `unknown-key`, `bad-signature`, `legacy-payload`, `agent-not-submitter`, `human-submitted-agent-metadata`, `unsignable-field`, `note-without-evidence`, …). The stored row keeps the principal id and the credential's public prefix only. A reader compares the SHA-256 of the note bytes with the stored digest, so a note pushed to the notes ref around Kvarm reads as `declared`. `GET commits/:sha/attribution` returns the note's own `agent` and `actor` display names to any reader, but its `evidence.principal` and `evidence.tokenPrefix` only to repo admins: an attribution note is readable by anyone with read access, including anonymous visitors on a public repo (the admin-only audit export still shows both).

  Signed evidence is `{keyId, runId, signature}` in the attribution write. The signature is Ed25519 (WebCrypto) over the UTF-8 bytes of exactly seven newline-terminated lines, which bind the target repository and the submitting principal as well as the record's `model` and `promptHash` and the target commit:

  ```
  kvarm-provenance-v2
  repo:<repository id>
  principal:<user:<id> or agent:<id> of the authenticated submitter>
  run:<runId>
  model:<model>
  input:<promptHash>
  commit:<40-hex commit sha>
  ```

  The payload is built server-side from the authenticated submitter and the target repository, never from the request, so a signature replayed by another principal or against another repository fails verification. The retired `kvarm-provenance-v1` payload (the same lines without `repo:` and `principal:`) is recognized only to report such a signature as `legacy-payload`; it never verifies, so a record signed under it does not read as `verified`.

  Signed fields may not contain control characters (`unsignable-field`). Trusted keys are raw 32-byte Ed25519 public keys (base64url) whose id is the first 16 hex characters of their SHA-256: per repository through `add_provenance_key` (repo admins; revoked keys verify nothing new) or per instance through the `KVARM_PROVENANCE_KEYS` variable (comma- or whitespace-separated). Agent `modelFamily` values are self-declared at principal creation, so reviews and reviewer assignment report `modelFamilyEvidence: declared` for agents (`authenticated` for the `human` family) and label the cross-model preference with the weaker of the two levels.
- **Audit export.** `GET audit` (repo admins; anonymous `401`, otherwise the shared concealment rule) returns one record per commit Kvarm has seen through an attribution write or a ref update: agent, session, prompt hash, model, evidence level and basis, the attribution credential's token prefix, the gate pushes that made it a ref tip and the merges (`merge` for an explicit merge, `queue` for a train publication) that published it. Records are ordered by first-seen time (the database clock at insertion, never decreasing along a per-repository insertion sequence) with an opaque cursor, so pages stay stable and a commit recorded after a page was read always sorts after it; `since` (inclusive) and `until` (exclusive) filter on first-seen time. A commit's record carries its newest evidence row; when two writers attributed one commit concurrently, `GET commits/:sha/attribution` (which matches the note's digest) is authoritative. `format=ndjson` writes one record per line and then a `{"page": {…}}` line. The ledger is written by the git gate for confirmed refs only, in the background after the push (one extra D1 round trip, not awaited by the reply), and by the explicit merge concurrently with its record batch; both are best effort and never fail the push or the merge. Train publications are recorded by a trigger on the queue's own `published` transition, which carries the enqueuing principal (and an agent's token prefix; the queue does not record a human enqueuer's PAT id). Full tokens are never stored or exported.
- **Agent review policy.** See §0.4. Approvals are revalidated immediately before publication; agent approvals never satisfy a protected target's human-approval requirement.
- **Semantic conflict.** A composition that merges cleanly but fails a required check on the composed tree is a semantic conflict, distinct from a textual one.

## 10. Cost metering and budgets

- **Meter.** `cost/meter.ts` wraps bindings in counting proxies for every request. It counts D1 round trips with rows read and written, Artifacts RPCs, Durable Object calls, R2 class A and class B operations, queue sends, outbound subrequests and the Cache API result. The counters are application work counts, not a bill: CPU, duration, storage and post-response background work are not included.
- **Header.** Every response carries `x-kvarm-cost: d1=…;rr=…;rw=…;art=…;do=…;r2a=…;r2b=…;q=…;sub=…;cache=hit|miss|none|bypass`, with counts only.
- **Background work.** The queue consumer, Workflows and the `MergeLock` Durable Object log the same counters per message, step or run, and store the last run's counters where an API exposes them (for example a snapshot's `buildCost`).
- **Authority before metadata and content.** Every repository metadata and content response (REST, git gate, pages, compare, snapshots and MCP repository tools) runs one bounded indexed D1 authority lookup before returning anything, including a cached hit (§11.1). That lookup is the authority component (`d1 ≤ 1`, `rr ≤ 8`, `do = 0`), not a cap on the whole request. A fully cached body totals `d1 ≤ 1`; a response that also reads its own service row (snapshot metadata or download, workspace list, queue read, cold compare) totals `d1 ≤ 2`; a bounded paginated service read (the dependency list) totals `d1 ≤ 3`; an audit export page (§9) is the authority lookup plus one indexed read, `d1 = 2`. Writes authorize authoritatively and are not served from cache.
- **Other budgets.** The git gate makes no Durable Object call (`do = 0`). A cold compare costs at most `treeReads + blobReads + 3` Artifacts calls, with one documented exception of `+4` for a first-ever compare against a base off the head's first-parent chain in a colo with no cached token. Write endpoints batch their D1 statements; the queue consumer uses one D1 batch per message plus required work; an MCP tool call costs the same as the equivalent REST call. PAT `last_used_at` stamping is throttled to one write per token every 10 minutes.
- **Measured values.** [`docs/benchmarks/README.md`](benchmarks/README.md) records the median counters per endpoint, and `scripts/cost-sweep.mjs` re-checks every budget row against a deployed worker.

## 11. Tenancy, Nexus and the integration train

### 11.1 Tenant and principal model

- Users and organizations share one account-name namespace. Organizations have `owner`, `maintainer` and `member` roles; at least one owner always remains. Repositories accept explicit `admin`, `write` and `read` grants; members get no implicit private access. Durable agent principals belong to a user or organization and receive owner-minted, expiring tokens scoped to one repository and, for writes, a list of ref patterns. Agent tokens cannot mint credentials or escalate grants.
- `services/authz.ts` resolves the actor's role, the credential ceiling (token scopes) and public visibility in one decision; `services/access.ts` loads the credential, the repository's current row, the org membership and the repository grant in **one** authoritative D1 batch. Repository rows, memberships and grants are never cached, so a visibility flip, revocation or removal applies to the next request in every colo. The Cache API copy of a token never authorizes by itself. Unknown, deleted and revoked principals fail closed; private repositories the caller cannot read are concealed.
- Humans sign in through WorkOS AuthKit (`/auth/login`, `/auth/callback`, `/auth/logout`); without the WorkOS secrets those routes answer `503` and only tokens authenticate. Sign-in uses `state` and PKCE bound to a sealed, short-lived cookie. The session cookie (AES-GCM under a key derived from `WORKOS_COOKIE_PASSWORD`; `HttpOnly`, `Secure`, `SameSite=Lax`; 7-day absolute lifetime) names the platform user and carries no authority of its own; sign-out records its id in `session_revocations` so copies die with it: each request re-reads that user and resolves to the same `Actor` a PAT of that user would, so revocation, removal and visibility flips apply on the next request. The WorkOS refresh token is redeemed every 10 minutes and a refusal ends the session; requests racing on that single-use token adopt the winner's rotation (a colo-local, 60-second record), and a WorkOS outage defers the refresh rather than signing everyone out. A state-changing request counts the session only from the same origin, and session form posts also carry the session's synchronizer CSRF token. One middleware (`routes/pageCsrf.ts`), installed in `index.ts` ahead of every router, enforces this for all the HTML pages: an unsafe request authenticated by the session cookie has its form parsed (urlencoded or multipart; the handler re-reads the cached parse) and is refused with `403` before any handler runs when `_csrf` is missing, belongs to another session, or the body is not a parseable form. Bearer PATs and agent tokens are not ambient and pass untouched, and a cross-origin session post already does not count as the session. Only `/api/v1`, `/mcp` (JSON surfaces, where a session counts only from the same origin) and `/auth/logout` (which checks its own token and must not refresh the session it ends) are exempt, so a page route added later under any router is covered without opting in; `test/pageCsrf.test.ts` walks every mounted route that takes an unsafe method and fails if one escapes the middleware or is registered ahead of it. Handlers keep their own checks as a second layer. A first sign-in provisions a user from the email local-part in the shared namespace and never grants instance admin; existing PAT-only users are linked only explicitly (an instance admin's link, or the operator's opt-in verified-email match), never by sign-in alone.
- Removing a member deletes that user's org-repository grants in the same guarded statement as the membership, including when an owner removes themselves; the last-owner protection stays inside that operation. Re-adding a former member does not reactivate old grants.
- The receive-pack gate parses bounded command headers before object data and enforces repository and workspace-ref access, branch rules, reserved namespaces and non-fast-forward rules. Agent tokens cannot leave their granted workspace refs.
- Branch rules are opt-in per repository and ref pattern. A protected ref cannot be created, updated or deleted by a direct push (the instance admin included); it changes only through the merge paths, which enforce required checks and required approvals from human principals other than the change author, pinned to the head SHA, and, for a rule with `guardCompleteness: 'required'`, a `kvarm/guard` verdict that inspected every changed file (§0.3).

### 11.2 Intent and forecast service

- Workspaces record their declaration, base and head revision, actor and activity. The Nexus index stores declared and observed paths per workspace (with bounded prefixes for wide edits); forecast and overlap reads follow shared paths instead of comparing every pair of workspaces.
- Intent is declared at creation and updated later. Push processing reconciles the cumulative base-to-head changed-path set, so deletions and reverted edits leave the observed set.
- Declarations are non-exclusive. A forecast reports evidence, freshness, a confidence class (declared or observed), the matching workspaces, and `truncated`/incomplete reasons under explicit budgets and cursors. An empty or truncated forecast is not proof of compatibility. Prefix overlap works: a declaration of `src/` intersects an observed `src/a.ts`.
- Issues name paths too. The issue-path index (`services/intents/issuePaths.ts`) stores each open or closed issue's paths and prefixes under the same rules, and a change probes it with its changed entries, their ancestor prefixes and its collapsed prefixes as ranges, at creation and again from a head-moved hook on every push; the issues service turns hits on open issues into proposed links, replacing only proposals nobody has answered. Like every Nexus answer this is advice: a proposal closes nothing until someone confirms it.
- The index steers work; mergeability and composed-tree checks remain the correctness gates. This service is the single owner of overlap signal (§0.1).
- **Semantic dependency signal.** Path overlap misses causal conflicts: one workspace changes an exported API while another edits a consumer in a different directory. The forecast service adds an advisory semantic layer for that. It is a bounded, deterministic heuristic (`packages/review/src/semantic.ts`, regular expressions over comment- and string-masked source), not a compiler, a type checker or a language model.
  - *What it reads.* When the push consumer reconciles a workspace's observed set (the `intent-index` effect, and the seed of a composed workspace), it reads that workspace's changed files at its head tree and records: the import edges out of them, followed up to `depthMax = 2` hops (TS/JS `import`/`export … from`/`require`/literal `import()`, Python `import`/`from … import`, Go import paths inside the nearest `go.mod` module); the export-surface change of each changed TS/JS module against the base tree (names added and removed, a deleted module removing all); and its changed contract files, grouped into API families by path convention (`*.proto`, `*.thrift`, `*.avsc`, `openapi*`/`swagger*` YAML or JSON, `*.graphql`, `*.schema.json`, `*.d.ts`, files under a `migrations/` or `migrate/` directory; the family is the kind plus the directory). Only relative TS/JS specifiers and in-repo Python and Go modules resolve; bare packages, path aliases and workspace package names do not.
  - *Where it lives.* Edges are computed from the consumer's side at push time and stored in D1 (`workspace_semantic`, migration 0029) as repo paths and names only, never content (§2.2), next to the observed set and under the same newer-push guard; a workspace that leaves active loses its rows by trigger. Forecast and overlap therefore stay pure D1 index reads (`art = 0`, `d1 = 2`): a match is a probe of the stored edges against the query paths or another workspace's observed rows, not a repository scan, and no reverse-import index of the whole repository is built.
  - *Budgets.* Per reconciliation: at most 40 changed source files, 96 blob reads, 96 tree reads, 4 MiB of source, 256 KiB per file, 1.5 s, 300 edges, 200 imports per file, 24 export comparisons and 50 contract files. Per read: at most 200 semantic hits per forecast probe; per overlap request 2,000 import rows of the base scanned, 500 hits, 200 shared contract families with 40 workspaces each and 4,000 family pairs; 20 evidence items per match. When a budget bites the workspace's semantic record or the response says `truncated` with the reason; it is never silently empty. A failed analysis keeps the observed set and records the failure as the semantic truncation reason; so does an observed set collapsed into directory prefixes, whose changes other workspaces' edges cannot be matched against.
  - *Confidence classes.* Path matches stay `observed` and `declared`. Semantic matches are reported separately under `semantic`, in three lower classes: `semantic:export` (the imported module removed or renamed a name the consumer imports), `semantic:import` (an imported module, or a Go package directory, changed) and `semantic:contract` (contract files of one API family). Each match carries the edge chain as evidence, the revision the edges were read at (`semanticHeadSha`, `semanticAt`) and the workspace's own truncation.
  - *Advisory only.* An empty semantic forecast is not proof of compatibility; the heuristic misses aliases, reflection, generated code and runtime contracts. Nothing gates on it: no push, merge, queue entry, check or ranking reads `workspace_semantic`. Exact-tree CI and mergeability remain the correctness gates. `semantic=0` on forecast and overlap leaves the layer out.

### 11.3 Draft dependency lifecycle

- A workspace may pin another workspace in the same repository at an exact revision. Chains are at most 4 deep, a workspace has at most 8 direct pins, and cycles are rejected with the offending path.
- Pins are `active`, `stale`, `satisfied` or `broken`. Source movement marks a pin stale; abandonment or ejection marks it broken; a landing satisfies it only when the pinned content is preserved in the published history. A SHA never counts as landed merely because a related change merged.
- Dependent contributors choose to repin, detach, or rebase or compose explicitly. Kvarm never rewrites a base or ref automatically.
- The train respects dependency order, and unresolved stale or broken pins cannot publish (`services/dependencyGate.ts`).
- **Landing settlement is bounded and durable.** Each settlement invocation processes a fixed number of pages of incoming pins; each page is one D1 batch fenced by the exact landing identity and pin revision, and also records a wake mark for each affected dependent. If work remains, the landing is handed to two independent owners: a continuation message on the existing event queue, and a settlement intent stored in the target ref's `MergeLock` Durable Object together with its alarm in one storage transaction. Wake marks follow a claim, send, confirm lifecycle on the fenced-claims machinery, so overlapping owners never both act on one mark. The alarm re-derives remaining work from D1, settles bounded pages idempotently, kicks queued dependents, resumes open `auto` dependents, and re-arms only while fenced work remains. One residual is accepted: a kick whose confirm failed may be sent once more after its claim lapses, which publication fencing absorbs.

### 11.4 Bounded integration train

- The queue keeps per-repository, per-target-ref partitions of immutable candidates in enqueue order, with the states queued, preparing, checking, ready, publishing, published, ejected and stale, the expected base and head, the approved tree, the check identity and an attempt generation.
- A train run takes the partition's D1 run claim, then composes the first 8 active entries in order, each on top of the previous candidate's prepared result, and asks the checks gate about each exact composed tree. At most 4 candidates are checking at once. Expensive merge, guard and CI work happens outside any publication lease. Admission is bounded: 64 active entries per repository, then `429 QUEUE_FULL` with `Retry-After: 30`; stale policy or revision answers `409`.
- Publication revalidates the current head, contributor policy, authorization, approvals and the exact composition check identity, acquires a short (30 s) generation- and owner-fenced lease in `MergeLock`, and moves the ref through receive-pack with the expected old value, parsing the status. The registry head never advances before the git ref is confirmed. A stale generation can neither release a successor's lease nor report success. An expired lease is recovered by its alarm, which kicks the train before clearing it.
- **Publications are crash-consistent.** The batch that claims an entry for publication (`ready` to `publishing`, a new generation) also writes its publication intent: repository, ref, old and new SHA, head, tree, entry, claimed generation, attempt and lease generation. Nothing is sent without one, and nothing is sent with less than `RECONCILE_LIMITS.sendMarginMs` of lease left. A confirmed push is recorded in one D1 batch that publishes the entry, merges the change, satisfies its pins and resolves the intent, still under the lease, which is released only afterwards. A refusal before the send withdraws the intent with the entry's own write; a definite `stale` or `rejected` reply resolves it as `moved` or `not_applied`. Any other reply (lost, garbled, or a send that threw) is never guessed at: the publisher reads the ref back and reconciles, and if even that read fails the entry keeps its claim with the intent pending and the run kicks the train again for when the entry counts as abandoned. A send refused for lack of lease time costs the entry no attempt.
- **Reconciliation** decides a pending intent from the actual ref only. A `publishing` entry older than twice the lease TTL is presumed abandoned; the next pass (kicked by the lease alarm, the run's own backoff or any later kick) reconciles at most `RECONCILE_LIMITS.perPass` of them with the target value its single ls-refs already read, so reconciliation adds no ref read. Ref at the new SHA, or with the new SHA under it (a bounded walk of `RECONCILE_LIMITS.maxCommitReads`: someone already built on the landed publication): the record is completed exactly once, through the same batch and side effects (pin settlement, attribution note, CI ref cleanup) as a confirmed push, which run after the lease is released. Ref at the old SHA: the push did not happen; the entry returns to the train with one more attempt (the abandonment wait is that attempt's backoff; a publisher's own inconclusive reply backs off through the run). Ref anywhere else: another writer moved it; the entry recomposes on the new tip (or goes stale as `BASE_KEPT_MOVING` once its attempts are spent and the walk was not cut short), and nothing is overwritten. Every write is fenced by the intent's generation, so a stale publisher or a repeated reconciliation writes nothing, and a crash mid-reconciliation leaves the intent pending for the next pass. Because Artifacts knows nothing of D1 fences, a push that outlives its lease can still land after reconciliation saw the old value; the entry's next composition then finds its head already in the target, and when one of the entry's newest `RECONCILE_LIMITS.lateIntents` intents that reconciliation resolved from a ref read (a definite `stale` or `rejected` reply proves its push never applied) is at or under the tip, the record is completed instead of dropped.
- **The intent lives in D1, not in `MergeLock` storage.** The registry update must commit atomically with the intent's resolution, and both are fenced by the queue entry's generation, which lives in D1; an intent in Durable Object storage would need a two-store protocol with its own crash window between the record and the intent's removal. The D1 row costs no extra round trip (it rides on the claim batch and is written only when the claim applied) and no extra lease call. `MergeLock` keeps owning only the lease and its expiry alarm, which restarts the train after a crash.
- **A reconciled publication surfaces in the events ledger and on the entry.** Each reconciliation outcome appends one `kvarm.queue.publication_reconciled` CloudEvents record to `events` (outcome `completed`, `not_applied` or `moved`, with the intended and the observed SHA, the change number and the generation); its id names the intent and the outcome, so it is recorded once. A publication completed by reconciliation is a normal `published` entry and `merged` change, with entry reason `PUBLICATION_RECONCILED`; an entry sent back carries `PUBLICATION_NOT_APPLIED` or `PUBLICATION_MOVED` in `GET queue` and `GET train` until the train next writes it. Intents stay in `merge_publication_intents` as history.
- Required checks run on the actual composed tree; path-disjoint edits are not treated as semantic proof. A failing composition ejects or re-prepares only the affected entries. Foreign head movement invalidates and re-prepares affected candidates with bounded retries.
- Fast-forward and three-way merge graphs and the contributor's policy are preserved. `services/fencing.ts` provides the same generation/owner-fenced expiring claims for CI jobs and agent tasks.

### 11.5 Events and snapshots

- Artifacts `repo.pushed` events reach the `kvarm-events` queue through one account-level subscription. For each message, one ingest D1 batch records the event, advances `pushed_at` monotonically, moves the ref position only for a newer event and refreshes the heads of open changes on that branch. Each downstream effect (cache invalidation, snapshot build, `kvarm/guard`, CI dispatch, Nexus index, train kicks, issues closed by commit messages on the default branch and guard findings filed from it) runs and is recorded independently, so a redelivery runs only what is missing. Out-of-order pushes cannot roll state back; a genuine repeated transition (A→B→A→B) is still processed.
- Snapshots are addressed by commit: per-commit metadata points at an immutable per-tree tarball in R2, so commits with identical trees share bytes. `SnapshotBuilder` walks the tree in bounded Workflow steps. Reading metadata never starts a build.
- Tarballs are stored zstd-compressed: each bounded build step emits one zstd frame of the tar bytes it produced, and the stored object is the concatenation of the step frames (one frame is always a whole step's output, so a retried step never rewrites an earlier frame). The tree row records `encoding` and `encoded_size` next to the plain tar `size`; rows and objects written before compression carry `encoding` NULL and are served as plain tar. `GET snapshots/:sha/download` negotiates with `Accept`: a client listing `application/zstd` gets the stored bytes as `application/zstd` (the CLI decodes frame by frame), any other client gets the tar decompressed in the Worker through `FixedLengthStream(tarSize)`. The content-addressed cache entry holds the stored representation once and both branches serve from a hit.
- Outbound webhooks. Platform events are CloudEvents 1.0 envelopes in the `events` ledger: type `kvarm.*`, `processed_at` NULL, `source` `/repos/<owner>/<name>`. A trigger fans each one out into a `webhook_deliveries` row per active hook of the repository subscribed to the type, inside the statement that wrote it; triggers on the state transitions themselves emit `kvarm.change.merged`, `kvarm.change.ejected`, `kvarm.check_run.completed` and `kvarm.escalation.opened`, so every write path (explicit merge, auto merge, the train, the checks API, the CI report, reviews) is covered and writes nothing unless a hook subscribes. A type already written to the ledger in that shape is subscribable through one entry in `WEBHOOK_EVENT_TYPES`, as `kvarm.queue.publication_reconciled` (§11.4) is. No request path or train step calls an endpoint: a pending delivery becomes a `kvarm.webhook.delivery` message on `kvarm-events`, sent by the pump (after each consumer batch and from the once-a-minute cron trigger, so an event recorded on a request path can wait up to a minute; the Worker's `scheduled` handler dispatches on the cron expression, so that trigger runs only the pump and the prune, and the 6-hour trigger `0 */6 * * *` runs only the fleet sweeps) or by the previous attempt as a delayed message. An attempt claims its row under a 60 s lease, POSTs the stored envelope with `x-kvarm-signature: sha256=HMAC(secret, "<timestamp>.<body>")`, follows no redirect, times out after 10 s and reads at most 4 KiB of the answer. Failures retry after 30 s, 2, 8 and 32 min and 1 h (6 attempts); 15 consecutive failed attempts disable the hook and record `kvarm.webhook.disabled`. Delivery is at least once and unordered; the envelope `id` is the idempotency key. Targets are `https` only and may not be private, loopback, link-local or reserved IP literals or local names; the Worker cannot resolve DNS, so a public name pointing at a private address is not caught here. Terminal deliveries older than 14 days are pruned by the cron in batches of 200. The pump is one indexed read per consumer batch that carried platform work, plus one write and one `sendBatch` when deliveries are due; an attempt is two D1 batches, one subrequest and at most one queue send. Attempts in a consumer batch run in three concurrent lanes (a Worker invocation holds at most six outbound connections, and an attempt's timeout starts when it calls fetch), beside the in-order push, train and settlement messages. An attempt is never made past the bound, even after one died holding its lease. Merge-queue exits to `ejected` and to `stale` are both `kvarm.change.ejected`, told apart by `data.state`. A failure to open the signing secret (`WEBHOOK_SECRET_KEY` missing or changed) sends nothing and never counts toward disabling the hook.
- Kvarm never deletes repository refs, user code or history automatically; an explicit abandon deletes only its workspace ref. Growing lists are paginated, comparisons and output are bounded, and runners poll with backoff.

### 11.6 Human and agent surfaces

REST, MCP and the CLI are thin adapters over the same services, generated from one operation registry (§0.1). They cover organizations, members and grants, agent credentials, reviews and escalations, workspaces, intents, forecasts and dependencies, the train and queue, tasks, candidates, compositions and arenas, attribution and decisions. CLI errors exit non-zero with an actionable message; MCP returns the same state and errors as REST.

The server-rendered human surfaces sit on the same services, never beside them. The repository pages (tree, blob, commits, branches) are joined by the coordination pages — repository activity (`services/activity.ts`: active workspaces with agent model families, declared intents, pin chains and the Nexus overlap pairs of one base), candidate comparison (arenas and any 1–8 workspaces, ranked, diffed against the base and each other, with duplication reported separately; selection is one form POST over the same service the REST route uses) and the train view (`services/trainView.ts`: the live entries per target, recent exits with their reasons over `idx_mq_exits`, and the open resolve-conflict tasks), which polls by reload. The compare page (`routes/comparePages.ts`) renders the changed-file list server-side from `services/compare.ts` — structure first, JavaScript-disabled users still get the list — and a small hand-written module (`public/assets/diffClient.js`, geometry probed headlessly in `apps/platform/test/diffClient.test.ts`) expands per-file diffs in a virtualized viewport of fixed 20 px rows: about 96 mounted rows for any file size, deterministic scroll anchoring, and lazy per-file fetches from the content-addressed file-diff API. Every coordination page is composed of bounded indexed reads and conceals private repositories through the shared authority lookup; anonymous public compare views are edge-cached like the tree pages, pinned immutably for SHA…SHA ranges and keyed by the repo view generation otherwise.

The review pages (`routes/reviewPages.ts`) put the human side of §0.4 on the same services. `/inbox` (`services/reviewInbox.ts`) lists the changes the review gate holds for a human (an open escalation, a protected-path or final-selection escalation not yet recorded, too few approving reviews for the policy or too few human approvals for a protected target) across every repository the viewer may review. One query reads the candidate repositories (owned, administered through an organization, write-granted, or every one for the instance admin; only those with a candidate change; at most 100, newest push first, with a `truncated` notice beyond) together with the viewer's membership and grant, and each is decided by `authorizeRepo` with the `write` need on the page transport, the same policy a repository page applies. A page reads at most 50 candidate changes (25 by default), newest first under an opaque `(created_at, id)` cursor, keeps those `reviewGate` blocks under the target's branch rules, grouped by the first reason each waits for (reviewers disagree, changes requested, protected target, arena final selection, awaiting approval). Each row links to the change page, the risk-ordered compare of base…head and the verdicts, and shows up to 8 newest reviews with the reviewer's model family and its evidence label (agents' families are `declared`, §9) and up to 8 open escalations. The change page (`/:owner/:repo/changes/:number`) renders the review packet: gate blockers, escalations, verdicts and a provenance panel. An approval of an older head whose principal has not approved the current one is marked stale on both pages, because it no longer counts. Approve, request changes and resolve are form posts that call `submitReview` and `resolveEscalation`, the services behind the REST routes and MCP tools, with a required note (at most 4,000 characters) that becomes the review body or resolution note. After the write succeeds, the post records a decision through `recordDecision` with `{task: "change:<number>", chosen: "<verdict>@<head>" or "<resolution>:<reason>", rejected: [], reason: <note>}`, so `get_context task=change:<number>` returns the human's reasoning. Measured `x-kvarm-cost` on the test fixture: the inbox is `d1=6` (credential, candidate repositories, the pending page, one batch of reviews and escalations, and the two shell reads), the change page is `d1=6` with no Artifacts call, and a decide post is `d1 ≤ 5`.

The provenance panel on the commit and change pages reads the evidence ledger (`attribution_evidence`, the newest row for the commit, as the audit export does), so neither page reads the notes ref for it. It shows the agent, session, prompt hash, model, evidence level with what the level proves and the reasons it is not higher, plus the decisions linked to the change (the change page's own `change:<number>` task; on a commit page, the changes that published the commit according to `ref_updates`), with chosen and rejected candidates and their reasons, at most 5 and a truncation note. A commit or change with neither renders no panel at all. The submitting principal and token prefix appear only to repository admins, as in `GET commits/:sha/attribution` (§9). A note pushed around Kvarm has no ledger row and therefore no panel; `GET commits/:sha/attribution` stays the authoritative reader of the note itself.

- **Before WorkOS sign-in.** Every page action works with a human PAT that has the `api` scope, sent as `Authorization: Bearer`, so a deployment without the WorkOS secrets reviews from the pages with exactly the REST authority. Bearer posts need no CSRF token because the credential is not ambient. Agent tokens and PATs without `api` act as anonymous on pages: they read public pages and are sent to sign in from `/inbox`. Agents review through REST and MCP, and only humans resolve escalations there as here. A signed-in session gets the same actions, and every one of its forms carries the session's CSRF token (§11.1).
- **Prompt hashes are opaque.** Kvarm stores no prompts, and the hash's algorithm and input belong to whoever produced it, so the pages show the value verbatim in monospace and link it nowhere. A `verified` record proves only that a trusted signer bound that hash to the commit (§9).

### 11.7 Arenas and deferred experiments

An arena is an explicit candidate set of 2–8 workspaces created together from one brief and base (§0.1). The existing candidate ranking compares them and reports deliberate duplication separately. The caller selects a winner through the normal merge policy, and selection opens a human escalation (§0.4). Losing candidates stay open until explicitly abandoned; nothing is spawned or selected automatically.

Four further experiments (contract capsules, semantic packets, hotspot suggestions and priority credits) are designed but deferred (§0.2).

### 11.8 Scale evidence

Scale claims rest on one measured live run of 100 workspaces through the train, recorded in [`docs/benchmarks/fleet-100.md`](benchmarks/fleet-100.md), plus the per-endpoint counters. The drivers are bounded (one driver, at most 3 git children and 5 HTTP requests in flight, a 10,000-request campaign ceiling) and honor rate limits. These measurements do not support claims of universal thousand-agent throughput or a monetary bill.

### 11.9 Revert change sets and incident webhooks

- **Change kinds.** `change_sets.kind` is `change` (opened from a branch), `revert` (built by `services/reverts.ts`) or `conflict-resolution`. The kind is descriptive only: guard, CI, mergeability, merge and the queue treat every kind the same way.
- **The revert.** `POST reverts {sha | changeNumber}` reverts onto the tip of `base` (default: the reverted change set's base, else the default branch). The tree is gitops `revertTree`: the inverse three-way merge `merge3(base = reverted commit, ours = base tip, theirs = parent)`, which is what `git revert` writes; a merge commit reverts relative to its first parent (`git revert -m 1`), a root commit to the empty tree. A merged change set reverts relative to the target it landed on (`base_sha` recorded at the merge), which also undoes a fast-forward of several commits as one revert. No resolver runs, so a hunk git would stop on is `409 REVERT_CONFLICT` with the paths and nothing is written; a revert that changes nothing is `409 NOTHING_TO_REVERT`. The work spends the merge budgets (`MERGE_BUDGETS`). The commit has the base tip as its only parent and git's revert message (plus the reason).
- **Revert branches.** Kvarm writes the commit to `refs/heads/kvarm-revert/<sha7>-<8 hex>` through the direct writer and then opens the change through the ordinary create path. The namespace is platform-reserved (§2.10) for every git credential, agent tokens included, so the head that the guard and CI judged cannot be replaced by a push. Branches are never deleted automatically (§11.5), except the branch of a revert whose change could not be opened; a merged or closed revert keeps its branch, like a merged workspace keeps its ref.
- **No queue priority.** A revert enqueues like any change and waits behind earlier entries. The train has no priority machinery, and a lane that skipped earlier candidates would publish trees nobody checked against the reverted tip. When an incident cannot wait, a human sets the revert's policy to `review` (a draft never merges) and merges it explicitly (`PATCH changes/:n {mergePolicy: "review"}`, then `POST changes/:n/merge`), which still requires its checks.
- **A revert that stops applying.** When the base moves so that an open revert change conflicts, the change is marked `conflicted` like any other but gets no `resolve-conflict` task: its head is platform-reserved, so no completion could move it. The remedy is a fresh revert on the new tip (`POST reverts` again) and closing the old change.
- **Incident webhook secret.** HMAC verification needs the secret itself, so a stored hash cannot verify and a stored or encrypted secret lets a reader of D1 (with the encryption key alongside) sign deliveries. Each repository's secret is instead derived: `HMAC-SHA256(INCIDENT_WEBHOOK_KEY, label, repository id, nonce)`, where `INCIDENT_WEBHOOK_KEY` is a Worker secret and the nonce is random per rotation. D1 stores the nonce and SHA-256 of the secret (shown as a 12-hex fingerprint); neither signs anything without the Worker secret. The secret is shown once, at rotation; rotation replaces the nonce, so the previous secret stops verifying immediately. Without the Worker secret the feature is off. Changing the Worker secret invalidates every repository's secret.
- **Deliveries.** `POST incidents` carries a CloudEvents 1.0 event (structured JSON; `subject` is the commit, `id` the idempotency key, `data.reason`/`base`/`mergePolicy` optional) and the headers `x-kvarm-timestamp` (Unix seconds, within 300 s) and `x-kvarm-signature: sha256=<HMAC-SHA256(secret, "<timestamp>.<raw body>")>`. The raw body (at most 64 KiB) is verified before it is parsed. A stale or missing header is refused before any D1 read; an unknown repository, a repository without a webhook and a wrong signature then answer the same `401 INVALID_SIGNATURE`, so deliveries cannot probe for private repositories, and nothing is written on any of them. The idempotency key is the event's `source` and `id` together, as CloudEvents defines uniqueness. A verified event claims its key in `incident_events` before any ref is written; a second delivery answers `200` with the change the first opened, a concurrent one `409 EVENT_IN_PROGRESS`, and a delivery whose revert was refused releases its claim so a retry recomputes. A claim abandoned for 120 s (a delivery that died) may be taken over; the revert branch is named after the event (`kvarm-revert/<sha7>-<8 hex of SHA-256(source, id)>`) and created by compare-and-swap from nothing, so the taking-over delivery adopts the change the first one opened, or replaces a branch the first one left without a change by a revert planned on the current tip. Migration `0031` also allows one change per revert branch (a unique index), so two deliveries that race past those checks never both open a change. An event is immutable: the same source and id naming another commit is `409 EVENT_ID_REUSED`. Unknown repositories cost the same key derivation and verification as known ones, and deliveries are throttled per repository and client IP in a bucket of their own. Replays inside the window are absorbed by that idempotency. The revert is authored by Kvarm (no actor) and honors branch rules like any change.
